# Deploying to Render

This backend deploys to [Render](https://render.com) as a Docker web service backed
by managed PostgreSQL, using the [`render.yaml`](render.yaml) Blueprint in this repo.

There is **no separate build step** — Directus is a prebuilt app. "Building" here
means producing the Docker image (Render does this from the [`Dockerfile`](Dockerfile))
and running it. The image bakes in [`snapshot.yaml`](snapshot.yaml) and applies your
schema automatically on every deploy.

## What gets created

| Resource | Description |
|---|---|
| `thrive-directus` | Web service running the Directus Docker image |
| `thrive-directus-db` | Managed PostgreSQL database (internal-only) |
| `uploads` disk | 1 GB persistent volume mounted at `/directus/uploads` |

`KEY` and `SECRET` are generated by Render and stay stable across deploys. The DB
connection is wired automatically. Schema is applied on boot via `schema apply`.

## One-time setup

1. **Push the deploy config** (already done if you ran the steps with me):
   `Dockerfile`, `render.yaml`, and `snapshot.yaml` must be on the branch Render deploys.

2. **Create the Blueprint** — Render Dashboard → **New +** → **Blueprint** → connect
   the `Paras0218/thrive-directus-backend` repo. Render detects `render.yaml`.

3. **Fill the prompted env vars** (the `sync: false` ones):
   - `ADMIN_EMAIL` — your admin login email
   - `ADMIN_PASSWORD` — a strong password
   - `PUBLIC_URL` — leave blank for now; set it in step 5

4. **Apply** and wait for the first deploy. On first boot Directus runs migrations,
   creates the admin user, and applies your schema. Watch the logs for
   `Server started` and that `schema apply` succeeded.

5. **Set `PUBLIC_URL`** — copy the service URL (e.g.
   `https://thrive-directus.onrender.com`) into the `PUBLIC_URL` env var on the web
   service, then redeploy. This fixes admin-app asset/link URLs.

## Import your content (one time)

The schema arrives automatically; **content does not**. After the service is live,
run the import script locally, pointed at the Render URL. From `e:\directus-cms`:

```powershell
npm install   # if node_modules isn't present
$env:DIRECTUS_URL  = "https://thrive-directus.onrender.com"
$env:ADMIN_EMAIL   = "<the admin email you set on Render>"
$env:ADMIN_PASSWORD= "<the admin password you set on Render>"
node import-data.mjs
```

This logs in as admin, re-applies the same static token (so a frontend using
`static-token.txt` keeps working), and inserts the records from `data-export.json`.
It prints `IMPORT_DONE (0 failures)` when clean.

> The static token is read from your local `static-token.txt`, which is gitignored
> and only exists on your machine — that's why the import is run locally, not in CI.

## Updating later

- **Code/config changes** → push to the connected branch; Render auto-redeploys.
- **Schema changes** → locally run `npx directus schema snapshot ./snapshot.yaml` to
  regenerate the snapshot, commit it, and push. The next deploy applies the diff.
- **Directus upgrades** → bump the version in both `package.json` and the `Dockerfile`
  `FROM` tag together, regenerate the snapshot, then push.

## Notes & gotchas

- **Cost / plans** — the web service uses the paid `starter` plan because a
  persistent disk requires it. To trial for free, set `plan: free` and remove the
  `disk:` block (uploaded files won't survive restarts). See comments in `render.yaml`.
- **File storage** — for real production, prefer S3-compatible object storage
  (`STORAGE_*` env vars) over the disk, so files survive instance changes and scaling.
- **Region** — `render.yaml` defaults to `oregon`; change it (in both the service and
  the database) to the region nearest you. They must match for internal networking.
- **DB SSL** — internal Render Postgres connections don't need SSL. If you ever switch
  to the external connection string, add `DB_SSL=true` (or append `?sslmode=require`).
